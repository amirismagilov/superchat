# Встраиваемый интерфейс OmniCRM

Веб-интерфейс — ES-модуль без сборки и внешних CDN. Пользовательский элемент
`<omni-inbox>` изолирует стили через Shadow DOM. Самостоятельная страница
доступна по `/`, модуль — `/static/inbox.js`. Токены, пароли и коды не
сохраняются в localStorage, sessionStorage, cookies или URL.

## Встраивание в микрофронтенд

Рекомендуется проксировать `/api/*` и `/static/*` к сервису на домене CRM.
Хост-приложение получает короткоживущий JWT своего сотрудника от доверенного
сервера и передаёт его свойством элемента. Секрет подписи JWT браузеру не нужен.

```html
<omni-inbox id="sales-inbox"></omni-inbox>
<script type="module" src="/assets/messaging-bootstrap.js"></script>
```

```js
// /assets/messaging-bootstrap.js — модуль CRM, разрешённый её CSP.
import '/static/inbox.js';

const inbox = document.querySelector('#sales-inbox');
inbox.baseUrl = ''; // Корень API; по умолчанию текущий origin.

async function authorizeInbox() {
  // Реализуется на стороне CRM. Обмен не требует секрета подписи в браузере.
  const response = await fetch('/crm/session/messaging-token', {
    method: 'POST',
    credentials: 'same-origin',
    // Добавьте принятый в CRM механизм CSRF для её session-cookie endpoint.
  });
  if (!response.ok) throw new Error('Не удалось получить доступ к сообщениям');
  const { access_token } = await response.json();
  inbox.token = access_token;
}

inbox.addEventListener('omni-auth-required', authorizeInbox);
inbox.addEventListener('omni-ready', event => {
  // detail.user = { sub, tenant_id, role }; содержимого сообщений здесь нет.
});
inbox.addEventListener('omni-logout', () => {
  // Элемент очистил токен, черновики и загруженные сообщения из памяти.
  // Хост при необходимости закрывает собственный сеанс CRM.
});
await authorizeInbox();
```

JWT передаётся заголовком `Authorization: Bearer ...`. Не передавайте его
атрибутом HTML, query-параметром iframe или `postMessage` без проверки origin.
`inbox.token = ''` завершает сеанс элемента. При обновлении токена текущие
черновики очищаются; хосту лучше обновлять его до активного ввода сообщения
или предусмотреть согласованное сохранение черновиков на стороне CRM.

Для высоты внутри страницы:

```css
omni-inbox {
  display: block;
  --omni-inbox-height: calc(100dvh - 64px);
}
```

`baseUrl` задаётся до `token` и не включает `/api`. При размещении API на другом
origin нужны точный CORS allowlist на сервере, `connect-src` в CSP CRM и HTTPS.
Элемент делает запросы с `credentials: 'omit'`: авторизация API не зависит
от сторонних cookie. Текущая серверная CSP разрешает встраивание страниц
только с того же origin; микрофронтенд через ES-модуль не требует iframe.

## Общий список диалогов и поиск адресатов

Начальный экран показывает диалоги всех доступных рабочих аккаунтов в одной
таблице: клиент, последнее сообщение, мессенджер и аккаунт, время,
избранное, непрочитанные и ожидание ответа. Фильтры по аккаунту и мессенджеру,
поиск и страницы обрабатываются сервером; поиск не ограничен первой страницей.
При отсутствии фотографии показаны инициалы, без подставных аватаров.

«Новый диалог» ищет среди уже обнаруженных чатов по имени, названию компании
или идентификатору. Например, «ООО Ромашка» может дать несколько результатов:
каждый содержит конкретный канал и рабочий аккаунт. Выбор открывает именно
существующий диалог и не создаёт его копию. Одинаковые имена не считаются
доказательством, что это один клиент. Для нового адресата остаётся ручной ввод.

Контракт для другого микрофронтенда:

- `GET /api/inbox?q=&account_id=&channel=&limit=50&offset=0` возвращает
  `{items,total,has_more}`; `GET /api/recipients` использует те же параметры.
  Элемент включает `id`, `account_id`, `peer`, `title`, `channel`,
  `account_label`, `account_state`, `preview`, `last_activity_at`,
  `unread_count`, `stage`, `favorite`, `waiting_since`.
- `PATCH /api/conversations/{id}` принимает `title`, `favorite` и/или `stage`
  (`new`, `in_progress`, `done`). Название, установленное в CRM, сохраняется
  при последующих обновлениях имени из мессенджера.
- `POST /api/conversations/{id}/read` с `{last_message_id: N}` отмечает
  просмотренные входящие сообщения до **входящего** сообщения N данного чата.
  Передавать нужно ID фактически показанного сообщения с `read_eligible: true`
  в ответе списка сообщений. Исходящие, старый архив и исторический импорт
  не могут быть границей прочтения: их ID могут оказаться выше ещё не показанного
  нового входящего сообщения.
- `POST /api/accounts/{id}/actions` с
  `{action: "history", payload: {history_days: 365}}` запускает загрузку
  доступной истории подключённого Telegram, WhatsApp Web или MAX personal.
  Допустим период 1–3650 дней; пустой payload означает 3650. Выполненная задача
  подтверждает постановку фонового импорта, а не завершение всей выгрузки.
  Прогресс публикуется в `account.public.history_sync`: `state`,
  `chats_discovered`, `chats_completed`, `history_days` и ограниченный `reason`.

Прочтение хранится отдельно для каждого сотрудника в CRM. Оно не вызывает
отметку «прочитано» в нативном мессенджере. Избранное общее для диалога.
Поле `stage` сохраняется в API для совместимости, но в интерфейсе список
этапов не отображается.
Исторический импорт и сообщения, существовавшие до этого обновления, не
увеличивают непрочитанные. Ожидание ответа начинается с нового входящего после
последнего принятого провайдером исходящего; очередь и ошибка отправки его
не закрывают. Это текущий срок ожидания, а не средняя скорость работы менеджера.

## Возможности интерфейса

- Аккаунты сотрудника, диалоги по каналу, поиск по имени и идентификатору клиента.
- История с подгрузкой предыдущих 100 сообщений и опросом раз в три секунды;
  в скрытой вкладке опрос приостанавливается.
- Отправка текста, отображение очереди, доставки, прочтения и ошибок провайдера.
- WhatsApp Cloud: переключатель одобренного шаблона, его имя, код языка и
  текстовые параметры body по одному на строку. Шаблон должен быть заранее
  одобрен Meta. Поле сообщения в этом режиме сохраняет описание в истории CRM;
  клиент получает текст зарегистрированного шаблона. Header, media и кнопки
  шаблонов текущая форма не настраивает.
- Создание диалога с подсказками формата получателя для каждого канала.
- Формы подключений строятся по `GET /api/capabilities`; отключённый канал
  показывает причину и не позволяет создавать аккаунт.
- Telegram: телефон → код → пароль 2FA при необходимости, альтернативно QR.
  API ID/hash администратор задаёт один раз отдельной кнопкой настройки
  Telegram; менеджерам эти поля не показываются. WhatsApp Web: QR,
  инструкции и автоматическое подтверждение подключения.
  MAX personal: выбранный сервером способ входа, код, пароль либо QR.
- Окно успеха WA/TG открывается только после серверного `connected` и
  показывает подтверждённые провайдером данные аккаунта. QR берётся из
  `public.qr_data_url`; для Telegram отображается срок его действия.
  Повторные нажатия защищены от создания дублирующих задач; закрытие окна
  прекращает клиентский опрос задачи. Обработка аккаунта воркером продолжается.
- Проверка состояния и отключение выполняются фоновыми задачами. Для Telegram,
  WhatsApp Web и MAX personal запрашивается отзыв сеанса. Для WhatsApp Cloud,
  MAX Bot и SMSGateway CRM прекращает обработку; токен при необходимости
  отзывают в кабинете провайдера. Интерфейс опрашивает `/api/jobs/{id}`
  и показывает ответ сервера; успех не имитируется.
- Для WhatsApp Cloud, MAX Bot и SMSGateway окно аккаунта показывает URL webhook
  и уведомления провайдера. Администратор настраивает callback и проверку подписи
  у провайдера. Успешная проверка credentials сама по себе не подтверждает приём
  входящих: он проверяется отдельным реальным тестовым сообщением.
- Демо явно помечено и позволяет добавлять тестовое входящее сообщение только
  через отдельный dev endpoint. Работоспособность демо не подтверждает внешние
  подключения или доставку сообщений реальным клиентам.
- Адаптивный интерфейс: на узком экране отдельно открываются каналы, диалоги
  и переписка. Модальные окна поддерживают клавиатуру, фокус и Escape.

Начальная самостоятельная страница имеет атрибут `standalone`: показывает
демо-вход и форму JWT. Встроенный элемент без этого атрибута ждёт авторизации
хоста. В production `/api/dev/token` отключён сервером, и кнопка демо честно
сообщает об этом; для рабочего продукта хост использует свой механизм входа.

## Повтор отправки и безопасность отображения

Для новой отправки создаётся UUID `client_id`. Если ответ API потерян, интерфейс
сохраняет текст и UUID в памяти и предлагает повторить тот же запрос. Поле
ввода временно блокируется, чтобы редактирование не превратило повтор в другое
сообщение с тем же ключом. После подтверждения ответа текст очищается.

Статусы `failed` и `uncertain`, возвращённые очередью, не вызывают автоматической
повторной отправки. Для `uncertain` показана просьба проверить нативный чат.
Потеря всей вкладки уничтожает локальный UUID: после перезагрузки нужно сначала
проверить историю, прежде чем отправлять тот же текст вручную.

Весь текст клиента, названия аккаунтов и ошибки вставляются через `textContent`
или текстовые DOM-узлы. HTML сообщений не выполняется. Изображения QR принимаются
только как `data:image/png|jpeg|webp;base64,...`; внешние URL не загружаются.
Обычная переписка, вложения и идентификаторы не отправляются сервисам аналитики.
Вложения, групповые рассылки и rich text в текущий интерфейс не входят;
у текстового канала их не следует показывать как работающие.

## Проверка

Внешние API проверяются отдельно от интерфейса и требуют рабочих учётных данных.
Локальный UI-проход: открыть `/`, войти в демо, открыть диалог, отправить текст,
добавить тестовый входящий ответ, убедиться, что история сохраняется после
перезагрузки и повторного демо-входа. Для worker он должен работать отдельно
от API. Ошибки авторизации или внешнего провайдера должны оставаться видимыми.
