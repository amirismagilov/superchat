# Open source для CRM с личными рабочими аккаунтами

Проверено 14 октября 2026 года по исходным LICENSE, документации проектов и страницам релизов. Это оценка пригодности компонентов; наличие релиза и открытой лицензии не означает, что конкретная сборка выдержала 300 реальных аккаунтов. Звёзды GitHub не использованы как доказательство надёжности. Данные ниже — зафиксированный срез, а не автоматическое обещание «последней версии» при будущем развёртывании.

## Рекомендация

Для существующей CRM с собственными микрофронтендами разумно оставить свои пользователей, права, клиентов и UI, а обмен сообщениями вынести в отдельный сервис с адаптерами. Практический первый адаптер — **Telegram на Telethon 1.45.0**: пользовательская авторизация, сообщения и доступная аккаунту история. **TDLib** — более официальная альтернатива для долгосрочного транспортного слоя, если команда готова сопровождать C++/JSON sidecar. Это инженерный выбор, а не результат сравнительного нагрузочного теста.

Для WhatsApp основной производственный путь — официальный Cloud API через обычный HTTP-клиент и webhooks. Для существующих личных/рабочих аккаунтов, где Cloud API не даёт нужную модель, существует реально работающий класс linked-device решений: **WAHA**, **Baileys**, **whatsapp-web.js**. Их следует держать отдельным заменяемым адаптером с явным статусом experimental: открытая лицензия на код не даёт гарантий совместимости с WhatsApp и не заменяет условия платформы.

Если собственный операторский UI ещё не нужен, **Chatwoot CE** — самый короткий путь к готовому inbox, истории и назначению менеджеров. Однако сам по себе Chatwoot не реализует требование «войти в личные аккаунты всех четырёх каналов». Для личного Telegram, SMS с физической SIM и личного MAX нужны свои адаптеры/API inbox.

## Что именно означает «можно использовать в коммерческой разработке»

**MIT, BSD-2-Clause, Boost Software License 1.0 и Apache-2.0** допускают коммерческое использование и модификацию. Для поставки дистрибутива сохраняют тексты лицензий и обязательные уведомления; у Apache дополнительно учитывают NOTICE, обозначение изменённых файлов и условия патентной лицензии. Эти лицензии не требуют открыть весь самостоятельный код CRM только из-за использования библиотеки. Основание — тексты LICENSE в таблице, а не ярлык «open source» на главной странице.

**GPL и AGPL тоже допускают коммерческое использование.** GPL создаёт обязательства в отношении передаваемых копий/производных работ; простое взаимодействие с сервером по сети само по себе не равно передаче копии. AGPL §13 дополнительно требует предложить соответствующий исходный код модифицированной программы пользователям, взаимодействующим с ней удалённо. Отдельный контейнер сам по себе не отменяет требования лицензии; самостоятельный сервис с обычным HTTP-интерфейсом и включение кода библиотеки в одно производное произведение — разные ситуации. [Текст GPL-3.0](https://www.gnu.org/licenses/gpl-3.0.html), [текст AGPL-3.0](https://www.gnu.org/licenses/agpl-3.0.html).

У **Baileys** это практический нюанс, а не абстрактная оговорка. В [package.json v6.7.24](https://github.com/WhiskeySockets/Baileys/blob/v6.7.24/package.json) присутствует зависимость `WhiskeySockets/libsignal-node`; [её package.json](https://github.com/WhiskeySockets/libsignal-node/blob/master/package.json) и [LICENSE](https://github.com/WhiskeySockets/libsignal-node/blob/master/LICENSE) указывают GPL-3.0. Внутренний сервис компании и продажа клиентам Docker-образа — разные модели поставки. Для второй нужен разбор полного lockfile/SBOM и способа связи с CRM. Проверка GPL здесь не означает, что коммерческий сервис запрещён.

У **Chatwoot** исключение `enterprise/` явно прописано в корневой лицензии. [Enterprise LICENSE](https://github.com/chatwoot/chatwoot/blob/develop/enterprise/LICENSE) требует действующую подписку на соответствующее число мест для использования enterprise-кода в production; доступность исходников не делает его частью MIT CE. Нельзя копировать enterprise-функции в CE, отключая проверки лицензии. Дополнительные возможности вроде SLA и некоторых административных инструментов нужно сверять с выбранной редакцией/тегом; [официальное сравнение редакций](https://www.chatwoot.com/hc/user-guide/articles/1677776492-enterprise-edition).

У **Evolution API** добавлены требования к frontend-брендингу и уведомлению об использовании, доступному администраторам в настройках/документации. При несоблюдении дополнительных условий автор указывает необходимость коммерческой лицензии. Отдельно [release notes 2.4.0-rc1](https://github.com/evolution-foundation/evolution-api/releases) описывают runtime-активацию через внешний сервер: до активации business endpoints возвращают `503 LICENSE_REQUIRED`. Это причина исключить компонент из рекомендуемой основы; не рекомендация обходить проверки.

## Где готовые продукты расходятся с исходным требованием

**Chatwoot Telegram не равен обычному пользовательскому входу.** Штатная настройка использует BotFather token; с v4.3.0 поддерживаются и Telegram Business bots. Последние позволяют отвечать от подключённого бизнес-аккаунта, но имеют ограничения, включая окно ответа, и не дают универсального MTProto-доступа ко всей старой истории. Для задачи «после телефонного звонка менеджер первым пишет клиенту от своей учётки» нужен либо подходящий разрешённый сценарий Business, либо отдельный MTProto-адаптер. [Официальная настройка Telegram в Chatwoot](https://app.chatwoot.com/hc/user-guide/articles/1677838569-how-to-setup-a-telegram-channel).

**WhatsApp библиотеки не дают готовую надёжную историю.** Baileys отдаёт события и синхронизацию, но рекомендует собственное хранилище; auth keys меняются во время обмена, их потеря ломает доставку. Нужно сохранять сообщения и состояние сессии отдельно, обрабатывать reconnect и дедупликацию, не обещать загрузку всего старого архива. Эти требования прямо следуют из [README Baileys: auth state и data store](https://github.com/WhiskeySockets/Baileys/blob/master/README.md).

**SMS с рабочего номера требует контроля над этим номером.** Android SMS Gateway отправляет с физической SIM телефона; это полезный обход ограничения обычных SMS-провайдеров, но доступность теперь зависит от телефона, сети оператора, питания, Android background policy и разрешений. Внутренний CRM-лог после подключения можно хранить независимо от устройства. Исторические SMS до подключения нельзя считать гарантированно импортированными без отдельного проверенного механизма. [SMS Gateway for Android](https://github.com/capcom6/android-sms-gateway).

**MAX personal имеет кандидата, но доказательств зрелости недостаточно.** PyMax содержит рабочий публичный код и выпуски; это не официальный MAX Bot API SDK и не подтверждение production на 300 сотрудниках. Установка, контрактные тесты и даже успешный обмен одним сообщением не доказывают устойчивость reconnect/auth на длительном интервале. Уместен ограниченный пилот с контролем состояния и возможностью продолжить диалог в штатном приложении. [PyMax](https://github.com/MaxApiTeam/PyMax), [release 2.4.1](https://github.com/MaxApiTeam/PyMax/releases/tag/v2.4.1).

## Что требуется именно для 300 сотрудников

Число операторов и число подключённых аккаунтов считать отдельно. Если у каждого по Telegram, WhatsApp и MAX, получится до 900 долгоживущих мессенджер-сессий плюс SMS-устройства. Для каждого аккаунта нужен один активный владелец сессии; иначе несколько worker могут нарушить порядок событий и состояние ключей. Это архитектурное требование сервиса, которое не решается выбором лицензии.

Для WhatsApp текущий [WAHA FAQ](https://waha.devlike.pro/docs/overview/faq/) приводит ориентиры ресурсов: 100 NOWEB-сессий — около 4 CPU/8 GB; 500 GOWS — 5–8 CPU/25 GB. Это оценки автора для конкретных engines, не результаты наших тестов и не sizing всей CRM. Для 300 аккаунтов разумнее несколько независимых групп сессий с резервом, чем один общий процесс; маршрутизация должна сохранять соответствие `account → instance`. [Рекомендации WAHA по масштабированию](https://waha.devlike.pro/blog/waha-scaling-how-to-handle-500-sessions/).

При выборе готового Chatwoot нужны отдельные web и worker процессы, PostgreSQL, Redis и object storage — это соответствует [официальной production-архитектуре](https://developers.chatwoot.com/self-hosted/deployment/architecture). Для собственной CRM полезна та же граница: API/история отдельно от долгоживущих каналов, большие вложения отдельно от БД, очередь отправки отдельно от UI.

Перед общим запуском нужны проверяемые результаты: успешное восстановление сессий после рестарта, отсутствие межпользовательского доступа, сохранение входящих при падении UI, корректное поведение при отозванной авторизации, измеренная доставка под рабочей нагрузкой и восстановление резервной копии. Начинать с 5–10 реальных сотрудников, затем 30–50 и только после наблюдений расширять до 300. Ни один из рассмотренных upstream-проектов не снимает с интегратора обязанность проверить именно эту конфигурацию.

## Граница проведённой проверки

Проверены корневые LICENSE и указанные важные исключения, upstream-документация, видимые релизы и статус архивирования. Полный аудит всех транзитивных лицензий, CVE и исходников каждого проекта здесь не выполнен. Перечисленные версии не означают проведённый live-тест с Telegram/WhatsApp/MAX или оператором связи. Перед коммерческим распространением бинарного продукта нужно сохранить LICENSE/NOTICE и SBOM именно установленной сборки; условия будущего `main/master` могут отличаться от условий выбранного тега.
