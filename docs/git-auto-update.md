# Автоматическое обновление существующего пилота из GitHub

Источник: публичный репозиторий `amirismagilov/superchat`, ветка `main`, workflow `.github/workflows/ci.yml`. Сервер сам проверяет GitHub примерно раз в две минуты и обновляет существующий `/opt/omnicrm-pilot`. GitHub Actions не получает SSH-ключ сервера; новый входящий порт и webhook не нужны. Нужен исходящий HTTPS с сервера к `github.com` и `api.github.com`, а для сборки приложения — доступ к реестру образов и Python-пакетов.

Подготовленный механизм не означает, что он уже включён на сервере. Первую установку выполняет владелец через свой работающий SSH. Дальше ручное скачивание ZIP для каждого изменения не требуется.

## Что считается разрешённым релизом

Деплой разрешён только когда последняя попытка последнего запуска именно `ci.yml` завершилась `success` для точного SHA текущей `main`, с событием `push`, и обе записи `repository`/`head_repository` указывают на ожидаемый репозиторий. Проверка PR, workflow с другим путём, устаревший успешный запуск перед неудачной новой попыткой, другой SHA, отсутствие результата и сетевые ошибки не разрешают обновление.

GitHub API читается без PAT. При недоступности API или исчерпании лимита публичных запросов обновление откладывается; обхода проверки CI нет. Когда текущий SHA уже успешно развёрнут, повторный опрос читает только Git-указатель `main` и не вызывает API Actions.

Код извлекается из отдельного bare-репозитория `/opt/omnicrm-pilot-autoupdate/repository.git` по точному SHA, а не через `git pull` в рабочий каталог приложения. Перед деплоем повторно проверяются `main` и результат CI. После первого успешного отслеживаемого деплоя новый SHA должен быть потомком последнего развёрнутого SHA: откат ветки или расходящаяся история блокируются.

Право менять `main` и её workflow фактически разрешает запуск кода обновления на сервере с root. Ограничьте доступ к ветке доверенными разработчиками, включите проверку PR и защиту workflow. Сам факт зелёного CI не заменяет проверку изменений владельцем репозитория.

## Однократная установка на сервере

Использовать `install_git_auto_update.sh` и `git_auto_update.py` **из одного проверенного релиза, закреплённого полным SHA коммита**. Не исполнять загрузку меняющегося `main` через `curl | bash`. После передачи этой пары файлов на сервер команда из их каталога:

```bash
bash scripts/install_git_auto_update.sh amirismagilov/superchat
```

Если файлы переданы непосредственно в одну папку без `scripts/`, команда из этой папки:

```bash
bash install_git_auto_update.sh amirismagilov/superchat
```

Установщик требует root, Git, Python 3, systemd, Docker и уже работающий закрытый пилот. Он сначала запускает существующую проверку `server_pilot.sh status`. Создаются только отдельный приватный каталог `/opt/omnicrm-pilot-autoupdate` и юниты `omnicrm-pilot-autoupdate.service` / `omnicrm-pilot-autoupdate.timer`. Файл `.env.pilot`, база, аккаунты, WAHA, порты и чужие сервисы установщик не меняет. Зависимости ОС автоматически не устанавливаются.

Каталог имеет владельца root и права `0700`; конфигурация и состояние — `0600`. Повторная установка для того же репозитория сохраняет состояние и заменяет только программу опроса/её собственные юниты. Другой репозиторий, неожиданные ссылки и юниты с чужой маркировкой не перезаписываются. Обновление самого механизма опроса требует повторной явной установки проверенной версии.

После `AUTOUPDATE_INSTALLED` таймер включён, но сообщение не подтверждает успешный деплой. Первый успешный CI-релиз устанавливает исходный отслеживаемый SHA; происхождение уже установленного вручную стенда заранее неизвестно. Его исходники перед обновлением дополнительно проверяет обычный updater по manifest.

## Что происходит при обновлении приложения

Проверенный коммит пакуется командой `python3 scripts/package_release.py --output-dir DIRECTORY`. Полученный архив и SHA-256 передаются `scripts/update_server_pilot.sh` из того же проверенного коммита. Применяются все ограничения [безопасного обновления пилота](server-update.md): сохранение `.env.pilot` и порта, сборка до остановки API/worker, приватная резервная копия, совместимые добавочные миграции, сохранение PostgreSQL и volumes провайдеров. Обычные обновления сохраняют контейнер WAHA. Единственная разрешённая миграция его настроек включает выбор IPv4 первым для закреплённого образа NOWEB; она пересоздаёт только этот шлюз с прежними volumes и восстанавливает прежние настройки при откате. Другие изменения постоянных сервисов блокируются.

Готовность фиксируется в `state.json` только после успешного завершения updater. При неудаче одна и та же пара «SHA + CI run + attempt» больше автоматически не пересобирается. Новая успешная попытка CI или явный `--retry` разрешают повторную попытку. Если процесс прервался и результат неизвестен, запись `in_progress` превращается в `previous_attempt_uncertain`, затем `retry_required`; это также требует проверки или новой попытки CI. Блокировка исключает одновременные опросы и сохраняется у дочернего процесса обновления.

Сервис имеет лимит выполнения 30 минут; при остановке группе процессов отправляется TERM, затем даётся до пяти минут на завершение и восстановление старого приложения обработчиком updater. После аварийного завершения состояние считается неопределённым. Автоматически восстанавливать базу из дампа механизм не пытается.

В журнал попадает только JSON со статусами, SHA и номерами запусков CI. Вывод дочерних Git/build/update-команд и сырые исключения не записываются: они могут содержать конфигурацию. Для разбора ошибки проверяйте состояние пилота и отдельную read-only диагностику; ключи и пароли в чат не пересылайте.

## Управление через SSH

Состояние последней проверки и последнего успешного деплоя:

```bash
python3 /opt/omnicrm-pilot-autoupdate/git_auto_update.py --status
systemctl list-timers omnicrm-pilot-autoupdate.timer
```

Проверить сейчас (команда возвращается сразу, работа выполняется сервисом):

```bash
systemctl start --no-block omnicrm-pilot-autoupdate.service
```

Повторить неудачную попытку после проверки причины; требование свежего успешного CI сохраняется:

```bash
python3 /opt/omnicrm-pilot-autoupdate/git_auto_update.py --retry
```

Отключить будущие проверки без остановки приложения:

```bash
systemctl disable --now omnicrm-pilot-autoupdate.timer
```

Это не прерывает уже начавшееся обновление. Перед ручным откатом приложения отключить таймер и дождаться завершения активного сервиса. Не удалять `state.json` для обхода защиты от отката: старый код может не поддерживать актуальную схему БД. Возвращать нужное поведение лучше новым проверенным коммитом через `git revert` с новым успешным CI.

Включить проверки снова:

```bash
systemctl enable --now omnicrm-pilot-autoupdate.timer
```

Типовые статусы: `up_to_date` — установлен текущий SHA; `deployed` — новая версия успешно установлена; `ci_pending` / `ci_missing` / `ci_failed` — обновление не разрешено результатом CI; `github_api_unavailable` — запрос не выполнен; `retry_required` — нужна проверка предыдущей неудачи; `non_fast_forward_blocked` — ветка не продолжает развёрнутую историю; `pilot_update_failed` — обычный updater завершился ошибкой.

Этот механизм рассчитан на существующий закрытый пилот. Он не меняет его на production-профиль, не создаёт публичный доступ и не заменяет резервное копирование/проверку совместимости миграций для эксплуатации большой командой.
