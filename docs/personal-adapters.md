# Личные корпоративные аккаунты WhatsApp и MAX

Эти два адаптера подключают аккаунт сотрудника как дополнительное устройство. Клиент видит обычный аккаунт менеджера. Это неофициальные интеграции: рабочий код проверен на моделях библиотек и моках протокола, но реальных входов и отправок в этой среде не было. Для 300 пользователей необходим отдельный пилот и нагрузочное испытание с реальными корпоративными аккаунтами. По умолчанию адаптеры выключены.

## Общая конфигурация

В окружении API и worker задайте `ENABLE_EXPERIMENTAL=true`. В API создания аккаунта разрешайте только документированные поля конфигурации. Все ключи `_waha_*` и `_max_*` — внутреннее состояние; принимать их от менеджера нельзя. Иначе можно подменить сессию другого сотрудника. Токены, challenge и курсоры сохраняет ядро в зашифрованном account config. Между poll и фиксацией событий конфигурация должна коммититься в одной транзакции: повтор после сбоя тогда воспроизводит ту же историю.

Историю первоначально импортируем за `history_days` (по умолчанию 30, максимум 3650). После первоначальной загрузки читаем новые сообщения. Полнота исходной истории ограничена тем, что отдаёт мессенджер. Ни WhatsApp linked device, ни MAX не гарантируют выгрузку всей переписки за все годы.

Поддержаны текстовые отправки и отображение входящего текста; сообщения без текста с вложениями имеют отметку `[Вложение]`. Скачивание/отправка файлов, редакции и удаления не реализованы. WhatsApp acknowledgment импортируется вместе с историей, но обновление статуса старого сообщения вне окна чтения не гарантировано; MAX receipt/read events пока не подключены.

## WhatsApp: WAHA NOWEB

1. Разверните отдельный self-hosted WAHA с движком **NOWEB**. Compose фиксирует Docker-образ `noweb-2026.9.2` с digest; для ARM используется `noweb-arm-2026.9.2`. Исходный GitHub-тег `2026.9.2` сверён с commit `90ba445a0e765701c8910f0fac08176250c3e0fd` на 2026-10-14. В этой версии подтверждены API `MessageTextRequest.id`, timestamp filters и persistent NOWEB store. Точные manifest digest и различия архитектур указаны в [локальной инструкции](local-accounts.md); перед использованием выполнить собственный live-тест.
2. Включите API key, установите `WAHA_URL=http://waha:3000` и `WAHA_API_KEY=...` в окружении backend/worker. URL и API key из account config игнорируются. URL не передаётся из браузера; redirects выключены.
3. Не публикуйте WAHA API в Интернет. Ограничьте доступ worker-сетью, используйте TLS при межсерверном трафике, зашифруйте volume сессий WAHA и его резервные копии. Ключ основной БД не шифрует файлы стороннего WAHA.
4. Создайте account `channel=whatsapp_web`, `config={"history_days":30}`. Выполните `action=login`, затем `action=sync`. При `qr_required` покажите PNG из `public.qr_data_url` (создан локальным QR-генератором) и отсканируйте в WhatsApp → Связанные устройства. Не отправляйте QR внешним сервисам генерации картинок.
5. Повторяйте `sync` до состояния `connected`. Если WhatsApp требует passkey, возвращается `action_required` и реальный `provider_state`; встроенное прохождение WebAuthn в этом адаптере отсутствует. Подтвердите действия в штатном WhatsApp/административном WAHA, затем проверьте `sync`.
6. Peer — номер в международном формате (`+79990000000`) либо WhatsApp chat ID (`79990000000@c.us`, `...@lid`, `...@g.us`). Raw NOWEB `@s.whatsapp.net` нормализуется в `@c.us` при импорте. События содержат `canonical_peer` и aliases номера с `+`/без `+`: ответ клиента попадает в исходный диалог CRM. Для `@lid` используется подтверждённая провайдером связь из `sendText` response `key.remoteJid/remoteJidAlt` (или `to` нормализованного ответа), либо `GET /api/{session}/lids/{lid}` → `pn`; связь хранится в шифрованном config. Если WAHA не знает номер для LID, аккаунты не склеиваются по предположению. Broadcast/newsletter чаты не импортируются.
7. `disconnect` вызывает provider logout и удаляет сессию WAHA. При ошибке конфигурация сохраняется, чтобы отзыв можно было повторить; простое удаление локального токена не считается отзывом.

Адаптер создаёт непредсказуемое уникальное имя `omni-<uuid>` и включает `config.noweb.store.enabled=true`, `fullSync=true`. Отдельные менеджеры получают отдельные WhatsApp сессии. Зафиксированная версия поддерживает несколько именованных NOWEB-сессий в открытой сборке; это не подтверждает ёмкость одного контейнера для всей команды.

Отправка: `POST /api/sendText` передаёт стабильный `id`, производный от outbox UUID. NOWEB `2026.9.2` возвращает raw Baileys message с `key`, а история возвращает нормализованный WAMessage. Адаптер строит ID raw-ответа по upstream `buildMessageId`, включая нормализацию device suffix и необязательный participant, чтобы последующее эхо сопоставлялось с исходящей записью.

Получение работает двумя проходами в каждом poll. Исторический проход читает `GET /api/{session}/chats`, затем `GET /api/{session}/chats/{chatId}/messages`: до 10 чатов по 100 сообщений, с сортировкой, offset и фиксированным временным диапазоном. Следующий диапазон перекрывает предыдущий на 300 секунд: время сообщения у провайдера может предшествовать его записи в хранилище WAHA. Курсоры сохраняются одной транзакцией с сообщениями; повторные ID не создают дубли.

Независимый проход читает последние 100 сообщений всех чатов через `GET /api/{session}/chats/all/messages` с сортировкой timestamp desc в пределах `history_days`. Поэтому новый ответ не ждёт завершения старого импорта или обновления списка чатов WAHA. `all` — специальный идентификатор persistent NOWEB store в закреплённом исходнике `90ba445a` (`ALL_JID`/`SqlMessagesMethods.getAllByJid`), а не обещание совместимости с другими движками и версиями WAHA. Собеседник берётся из raw `key.remoteJid` либо нормализованного `from`: у NOWEB это удалённый чат в обоих направлениях, а `to` у исходящего личного сообщения может отсутствовать. Кэш последних событий только в памяти и не скрывает изменения статуса или PN/LID; после ошибки транзакции или перезапуска worker события читаются повторно.

Это ограниченная сверка: сообщение, записанное с большой задержкой и уже вытесненное из последних 100 за пределы 300-секундного перекрытия, может потребовать повторного импорта. Для больших аккаунтов следующий этап — durable webhook ingestion с тем же dedupe и периодической сверкой истории. Тесты `test_whatsapp_incoming.py` воспроизводят задержанную запись, новый ответ во время импорта, replay и направление/LID; проверка на реальном аккаунте остаётся отдельным шагом.

При timeout, транспортной ошибке, HTTP 5xx или неразбираемом успешном ответе отправка помечается `uncertain`. Автоматического повтора нет даже при стабильном id: оператор сверяет фактическую историю. HTTP 429 возвращает retry-after ядру; политика очереди должна ограничивать повтор и скорость на аккаунт.

Лицензию проверяйте для точного artifact: [WAHA FAQ](https://waha.devlike.pro/docs/overview/faq/) описывает переход открытой версии на Apache-2.0 начиная с 2026.6.1, это не делает старые сборки/платные дополнения автоматически Apache-2.0. API сверены по [auth controller](https://github.com/devlikeapro/waha/blob/90ba445a0e765701c8910f0fac08176250c3e0fd/src/api/auth.controller.ts), [chats controller](https://github.com/devlikeapro/waha/blob/90ba445a0e765701c8910f0fac08176250c3e0fd/src/api/chats.controller.ts), [send DTO](https://github.com/devlikeapro/waha/blob/90ba445a0e765701c8910f0fac08176250c3e0fd/src/structures/chatting.dto.ts), [LID mapping controller](https://github.com/devlikeapro/waha/blob/90ba445a0e765701c8910f0fac08176250c3e0fd/src/api/lids.controller.ts) и [buildMessageId](https://github.com/devlikeapro/waha/blob/90ba445a0e765701c8910f0fac08176250c3e0fd/src/core/engines/noweb/utils.ts#L10). Подробная матрица проверенного контракта находится в [operations](operations.md).

## MAX: PyMax

В Docker-сборку уже включены **`qrcode[pil]==8.2`** и **`maxapi-python==2.4.1`**, импорт `pymax`. Не путайте SDK с одноимёнными пакетами других авторов. [MaxApiTeam/PyMax](https://github.com/MaxApiTeam/PyMax) распространяется по MIT; 2.4.1 помечена upstream как beta. Это SDK пользовательского протокола, а не официальный MAX Bot API.

В интерфейсе выберите «Подключить канал» → «MAX». Сначала показывается QR с инструкцией подтвердить вход на телефоне. После подтверждения проверяется профиль и появляется кнопка «Перейти в чаты». Есть альтернативный вход по номеру, коду и паролю двухэтапной проверки. API ID/hash, токен бота и регистрация приложения для этого сценария не нужны.

Создайте `channel=max_personal`:

- Для QR: `config={"login_method":"qr","history_days":30}` либо пустой config. `qr` (или `login` с `payload={"login_method":"qr"}`) → `qr_required`; изображение в `public.qr_data_url` создаётся локально. `public.expires_at` — Unix seconds. Worker вызывает `sync`, адаптер соблюдает интервал проверки из ответа MAX. При истечении QR — `login_required`, новый QR запрашивается явно.
- Для SMS: `login` с `payload={"login_method":"sms","phone":"+79990000000"}` → `code_required`, затем `code` с `payload={"code":"..."}`. Прежний способ задать телефон и метод в account config также поддерживается; переключение метода использует тот же аккаунт CRM.
- Для 2FA: `password_required` → `password` с `payload={"password":"..."}`. Пароль не сохраняется в session config. Ядро должно удалить обработанный auth payload из задания.
- Регистрация нового MAX аккаунта автоматически не выполняется. Заранее зарегистрируйте корпоративный аккаунт в штатном приложении.
- Для первого сообщения после звонка укажите peer **`+79990000000`** или **`phone:+79990000000`**. Адаптер вызывает документированный `client.search_by_phone()`, затем `client.get_chat_id(own_user_id, recipient_user_id)` и отправляет текст в вычисленный личный чат. Отдельная фиктивная операция «создать чат» не требуется.
- Если поиск номера недоступен, адаптер ищет точное совпадение номера среди контактов, уже полученных через login/sync. Он не импортирует адресную книгу и не добавляет контакты автоматически. Если MAX не раскрывает адресата ни одним из этих способов, возвращается `max_phone_not_found_or_private` **до отправки**. Практический следующий вариант — `user:123456`, если известен MAX user ID, либо попросить клиента начать диалог в MAX и выбрать импортированный чат. Доступность поиска и первой отправки зависит от настроек получателя и правил MAX; обойти их протокольной гарантии нет.
- Числовой peer **без `+`** всегда трактуется как **chat_id**, а не телефон и не user ID. Это сохраняет доступ к существующим личным/групповым диалогам. Форматы `user:...`, `phone:+...` устраняют неоднозначность.
- Найденный chat_id и aliases сохраняются до send, чтобы даже timeout и перезапуск worker не мешали сверить исходящую отправку с историей. Poll отдаёт `canonical_peer=chat_id` и aliases `+номер`, `phone:+номер`, `user:ID`; ядро сохраняет исходный ID диалога CRM при переходе к каноническому peer. При следующей явной отправке по номеру выполняется новый lookup; сохранённый alias не используется как доказательство, что номер всё ещё принадлежит тому же пользователю. Если тот же alias теперь разрешается в другой chat_id, `max_peer_identity_changed` останавливает отправку до проверки личности адресата.

QR использует `WebClient` и WebSocket, SMS — `Client` и TCP/TLS. Нужна разрешённая исходящая связь к официальным endpoint MAX, которые использует закреплённый SDK. Нельзя подменять endpoint через account config.

Авторизация реализована через поддерживаемый `AuthFlow`: `request_qr/check_qr/confirm_qr` либо `request_code/send_code`, затем `check_password`. Одна SDK bootstrap-задача держит соединение между шагами входа; неверный код или пароль не требуют заново создавать QR. Challenge, device ID и fingerprint сохраняются между запросами в шифрованном config, поэтому перезапуск worker между вводом кода и пароля не требует plaintext-файлов. Custom `StoreProtocol` сохраняет токен и device metadata туда же; SQLite/session.db не создаётся. Публичный API не отдаёт track ID/token и не принимает их от браузера. Ошибки SDK преобразуются в ограниченный набор кодов без raw payload.

`connected` возвращается после завершения SDK login и проверки собственного MAX user ID, а не по факту открытого сокета или сканирования. `max_self` связывает историю с исходным аккаунтом и переживает отключение. Вход другой учётной записью блокирует получение/отправку; явное отключение может отозвать такой сеанс, сохраняя прежнюю привязку истории. Доказанно отозванный token можно заменить явным новым входом; временная сетевая ошибка не стирает credentials. `disconnect` вызывает `client.logout()` и только после подтверждения удаляет локальную сессию.

`client.chats`, push-уведомления о новых chat_id и `fetch_history()` обеспечивают получение сообщений. Push — сигнал приоритетно проверить чат; содержимое повторно читается из истории, чтобы падение процесса не потеряло единственную копию. На poll выбираются до 10 чатов с уведомлениями плюс до 10 очередных чатов для равномерного обхода. Для каждого читается историческая страница до 100 сообщений и, если её граница уже в прошлом, отдельно последняя страница: свежий ответ не ждёт старого импорта. Сохраняется минутное пересечение между окнами. Это ограниченная сверка, а не гарантия полной выгрузки всей истории. Более 100 сообщений в одну миллисекунду на границе страницы вызывает явную ошибку `max_history_timestamp_boundary_overflow`, вместо скрытого пропуска.

Наблюдение из предоставленного HAR Umnico: запрос QR, затем проверки статуса приблизительно каждые 5 секунд; в записи успешное подтверждение наступило примерно через 30 секунд. Запись не показывает телефонный вход, ошибки или внутреннюю реализацию сервера конкурента. Наш адаптер не использует Umnico API, cookies или токены из HAR. `tests/test_max_personal.py` проверяет bootstrap установленного SDK 2.4.1 с подменённым транспортом; браузерные сценарии проверяют QR/код/пароль, ошибки и переход к чатам. Реальное подключение проверяется отдельно на рабочем аккаунте.

Отправка использует проверенные `SendMessagePayload` и `Opcode.MSG_SEND` через advanced API SDK, чтобы передать стабильный `cid`, полученный из UUID. High-level `send_message()` сам генерирует новый `cid`; поэтому он здесь не подходит для восстановления outbox. Семантика server-side dedupe не объявляется гарантией. Любой неподтверждённый результат этой операции — `uncertain`, требуется сверка, автоматического resend нет.

Источники: [AuthFlow и способы входа](https://github.com/MaxApiTeam/PyMax/blob/53103f0c8df32f36110cbe0bcbfc3ad82173808a/docs/auth.rst), [StoreProtocol](https://github.com/MaxApiTeam/PyMax/blob/53103f0c8df32f36110cbe0bcbfc3ad82173808a/src/pymax/session/protocol.py), [send/history service](https://github.com/MaxApiTeam/PyMax/blob/53103f0c8df32f36110cbe0bcbfc3ad82173808a/src/pymax/api/messages/service.py), [поиск пользователя и личный chat_id](https://github.com/MaxApiTeam/PyMax/blob/53103f0c8df32f36110cbe0bcbfc3ad82173808a/docs/users.rst).

## Проверки перед включением для всей команды

Запустить `pytest tests/test_personal_adapters.py`: моки проверяют QR/SMS/2FA, сохранение и восстановление сессии без файлов, стабильный nonce, uncertain на timeout, воспроизведение истории после сбоя, timestamp ties, неуспешный отзыв, первый контакт MAX по номеру, fallback к известным контактам, отказ до send при недоступном номере и объединение идентичности WhatsApp PN/LID по данным провайдера. Отдельно провести live-пилот на нескольких корпоративных аккаунтах: вход, сообщения в обе стороны, перезапуск во время авторизации, полный импорт истории, потеря сети после send, отзыв и повторное подключение. Затем испытать 300 подключений на целевом железе, измеряя p95 отправки/приёма, CPU/RAM на сессию, возраст очереди и задержку исторической синхронизации. До этого честный статус обоих адаптеров — экспериментальный, а не подтверждённая эксплуатация на 300 человек.
