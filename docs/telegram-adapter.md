# Telegram: корпоративный пользовательский аккаунт

Адаптер `app/adapters/telegram.py` использует MTProto через Telethon 1.45.0 (MIT).
Клиент видит обычный личный чат с рабочим аккаунтом менеджера. Бот для этого
канала не требуется. При увольнении сотрудника компания сохраняет номер и
доступ к Telegram; назначение владельца в CRM меняет доступ к истории CRM.

## Зачем нужны API ID/hash

Telegram отдельно проверяет, какая программа подключается и в чей аккаунт она
входит. API ID/hash — номер и ключ программы CRM. Номер телефона, код, QR и 2FA
подтверждают аккаунт менеджера. Реквизиты программы получают бесплатно один раз
для всей системы: менеджеры не регистрируют свои приложения. Это не бот, клиент
по-прежнему видит обычный аккаунт менеджера. QR-вход не отменяет настройку программы.

Самостоятельный MTProto-адаптер требует свои реквизиты приложения по
[условиям Telegram API](https://core.telegram.org/api/terms). Перенос формы
из браузера в серверную конфигурацию может скрыть настройку от менеджеров,
но не отменяет её. Даже собственная сборка открытого
[Telegram Web A](https://github.com/Ajaxy/telegram-tt) требует свой API ID/hash.

Без регистрации приложения можно автоматизировать оригинальный Telegram Web
в отдельных браузерных профилях. Такой коннектор в эту поставку не включён;
проверенного решения для 300 аккаунтов не найдено. Для него нужны отдельные
испытания доставки, устойчивых идентификаторов сообщений, входящих в неоткрытых
чатах, восстановления сессий и потребления ресурсов; изменения веб-интерфейса
могут нарушать автоматизацию.

[Telegram Business connected bots](https://core.telegram.org/api/bots/connected-business-bots)
используют токен бота вместо API ID/hash, но имеют ограничения для данной задачи:
[право ответа](https://core.telegram.org/bots/api#businessbotrights) действует
в чатах с входящим сообщением за последние 24 часа, а метода загрузки полного
старого архива нет. Обычный первый контакт отдела продаж после звонка такой
вариант полностью не покрывает.

## Однократная настройка администратором

Администратор регистрирует приложение компании на <https://my.telegram.org/apps>
и сохраняет его `api_id` и `api_hash` один раз для своей организации. Менеджерам
эти значения вводить не требуется. Все запросы API требуют JWT;
`GET /api/integrations/telegram` и `PUT /api/integrations/telegram` доступны только
с ролью `admin` и относятся к `tenant_id` из JWT.

Пример тела `PUT /api/integrations/telegram` — значения ниже демонстрационные,
их нужно заменить выданными Telegram:

```json
{"api_id":123456,"api_hash":"0123456789abcdef0123456789abcdef"}
```

`api_id` — положительное целое число, `api_hash` — строка из 32 шестнадцатеричных
символов. Ответ `PUT` и последующего `GET`:

```json
{"channel":"telegram","configured":true}
```

Значения хранятся зашифрованными в таблице `integration_settings`. API не
возвращает ни сам hash, ни API ID. `configured: true` подтверждает сохранённую
настройку; её действительность проверит Telegram при реальном подключении.
Менеджер видит только признак готовности через
`GET /api/capabilities` → Telegram → `connection.configured`.

При создании аккаунта параметры приложения копируются в его зашифрованную
конфигурацию. Последующее изменение настройки организации применяется к новым
аккаунтам и не меняет приложение уже существующей MTProto-сессии. Старые аккаунты
с индивидуальными `api_id/api_hash` сохраняют работоспособность. Создать новый
аккаунт с явно переданными `api_id/api_hash` теперь может только администратор.
Миграция `0002_telegram_integration` добавляет таблицу настроек, не изменяя
существующие аккаунты, сообщения и шифротексты сессий.

## Подключение менеджера по номеру

Нужен действующий пользовательский аккаунт Telegram на корпоративном номере.
`POST /api/accounts` создаёт запись CRM; это ещё не вход в Telegram:

```json
{"channel":"telegram","label":"Рабочий Telegram","config":{"phone":"+79991234567"}}
```

Сохраните `id` ответа. Далее отправьте `POST /api/accounts/{id}/actions`:

```json
{"action":"login","payload":{}}
```

Ответ `202` содержит ID задания. `GET /api/jobs/{job_id}` показывает его статус
`queued`, `running`, `done` или `failed`; состояние подключения читается отдельно
из `GET /api/accounts/{id}`. Успешная отправка кода переводит аккаунт в
`awaiting_code`. Код доставляет Telegram доступным для аккаунта способом;
обязательная доставка по SMS не обещается.

Отправьте код тем же endpoint действий:

```json
{"action":"code","payload":{"code":"12345"}}
```

Если включена двухэтапная проверка Telegram, состояние станет `awaiting_password`.
Тогда требуется облачный пароль Telegram, а не пароль компьютера или сервера:

```json
{"action":"password","payload":{"password":"ваш облачный пароль Telegram"}}
```

Неверный код или пароль оставляет возможность повторить текущий шаг;
`job.error` содержит безопасный код ошибки. После истечения кода запустите
`login` повторно. Состояние `connected` появляется после подтверждения сессии
Telegram и получения текущего пользователя через `get_me`.

## Подключение по QR

Используется та же настройка приложения организации. Для нового аккаунта номер
можно не вводить:

```json
{"channel":"telegram","label":"Рабочий Telegram","config":{}}
```

После создания отправьте `POST /api/accounts/{id}/actions`:

```json
{"action":"qr","payload":{}}
```

Аккаунт перейдёт в `qr_required`. `public.qr_data_url` содержит изображение QR,
а `public.expires_at` — срок действия текущего токена, полученный от Telegram.
На телефоне откройте Telegram → Настройки → Устройства → Подключить устройство
и отсканируйте код. При запросе 2FA используется описанное выше действие
`password`.

Воркер сам проверяет подтверждение и обновляет QR. Интерфейсу достаточно читать
`GET /api/accounts/{id}`; создавать новое задание при каждом опросе не нужно.
Явный `sync` во время ожидания QR проверяет авторизацию, а не импортирует историю.
Адаптер использует `auth.exportLoginToken`, при смене дата-центра —
`auth.importLoginToken`, и принимает успешный вход только после ответа Telegram.
Сессия и состояние ожидания сохраняются зашифрованными, поэтому процесс может
продолжиться после перезапуска воркера.

Одна попытка QR-входа ограничена пятью минутами. Затем аккаунт получает
`reauth_required` с `public.error: "telegram_qr_expired"`; повторный `qr` запускает
новую попытку. Срок отдельного QR задаёт Telegram и он может быть короче.
Закрытие окна браузера само по себе не отзывает попытку: для немедленного
отключения используйте действие `disconnect`.

## Подтверждённая личность и история

После успешного входа `public.identity` может содержать `phone`, `display_name`
и `username`, полученные от Telegram. Поля необязательны. До подтверждения
`public.phone` в шаге ввода кода — только введённый номер, он не считается
подтверждённой личностью.

Запись CRM закрепляется за Telegram user ID; эта привязка сохраняется после
`disconnect`. Попытка подключить к той же записи другого пользователя даёт
`telegram_account_identity_changed`, переводит аккаунт в `reauth_required` и
блокирует отправку из его очереди. Для другого Telegram-аккаунта создайте новую
запись CRM. Это сохраняет связь истории и очереди с исходным отправителем.
Для старых записей, отключённых до обновления и уже не содержащих user ID,
прежнюю личность автоматически восстановить нельзя: перед новым входом нужно
сверить владельца аккаунта.

После `connected` автоматически перечисляются обычные и архивные облачные
диалоги, включая группы, каналы, ботов и «Избранное». Служебный аккаунт 777000
исключён. История за 30 дней загружается порциями, отдельно от получения новых
сообщений. Для другого периода используется действие из интерфейса:

```json
{"action":"history","payload":{"history_days":3650}}
```

Период 1–3650 дней. Каталог читается по 50 диалогов с отдельным обходом архива;
на цикл импортируется страница до 100 сообщений одного диалога. Курсоры
сохраняются в зашифрованном config, новый запуск продолжает работу. Пустые чаты
также попадают в общий список. Прогресс доступен в `public.history_sync`.
Прежний ограниченный `sync` с `dialogs/messages` оставлен для совместимости,
но новый интерфейс использует `history`. `sync` при ожидании входа по-прежнему
проверяет состояние авторизации.

`phone_code_hash` и `StringSession` сохраняются в **зашифрованном** account
config. Сам адаптер не шифрует данные: это обязательная функция ядра. Сессия
позволяет войти в аккаунт без повторного кода; её нельзя отдавать браузеру,
писать в логи или включать в незашифрованные резервные копии. Код и пароль 2FA
не добавляются в config; ядро удаляет payload обработанного auth job.

Для первого сообщения после звонка используйте `+номер` в международном
формате либо `@username`. Для номера адаптер вызывает официальный
[`contacts.resolvePhone`](https://core.telegram.org/method/contacts.resolvePhone),
доступный в закреплённом Telethon 1.45.0. Адресная книга при этом не импортируется.
Метод работает, только если настройки приватности получателя разрешают поиск
по телефону. Если пользователь не найден/скрыт, возвращается
`telegram_phone_not_found_or_private` до отправки; практический вариант —
получить username от клиента либо попросить его начать диалог.

Telegram требует максимум один такой lookup за три секунды. Адаптер сохраняет
в account config ближайшее время следующего запроса и возвращает безопасный
`retry_after` при более ранней попытке. User выбирается строго по
`resolved.peer.user_id`, затем сохраняются его access hash и alias телефона.
Импортированные диалоги имеют устойчивый числовой user ID; после разрешения
ответ клиента связывается с исходным диалогом CRM по `canonical_peer`/aliases.

Access hash сохраняется рядом с сессией, поэтому адресация продолжает работать
после перезапуска воркера. При явной отправке по номеру/username выполняется
новый lookup. Если уже известный alias теперь принадлежит другому user ID,
отправка останавливается с `telegram_peer_identity_changed` до проверки
оператором.

## Доставка и восстановление

- Получение использует `updates.getDifference`, а не теряемую очередь событий
  в памяти. `pts/qts/date/seq` коммитятся ядром в одной транзакции с сообщениями.
  При rollback ядро закрывает экземпляр адаптера и создаёт новый из durable
  config. Повторно полученные provider IDs должны дедуплицироваться ядром.
- Первая авторизация устанавливает текущую точку отсчёта новых событий.
  Отдельный постраничный импорт читает старую историю. Входящие сообщения и
  исходящие из обычного приложения попадают в CRM с правильным направлением.
  Для групп и каналов используются отдельные marked peer IDs; каналы имеют
  собственные курсоры новых сообщений и не делят ID сообщений между чатами.
- После слишком долгого простоя сервер может вернуть `DifferenceTooLong`.
  Адаптер выдаёт `telegram_history_gap_sync_required`, сохраняя старый cursor.
  «Загрузить историю» разрешает восстановление: сначала фиксируется новая
  точка отсчёта, затем начинается обход диалогов и доступных сообщений за
  выбранный период. План импорта сохраняется вместе с курсором новых событий.
  Удалённые сообщения и сообщения за пределами периода восстановить нельзя.
  Обычный импорт при исправном курсоре не сбрасывает поток новых событий.
- Отправка использует `messages.sendMessage` с тем же 64-битным `random_id`,
  вычисленным из UUID outbox-сообщения. Идемпотентность API/outbox остаётся
  обязательной; протокольный nonce не заменяет долговечный журнал отправок.
- Timeout после начала send и неоднозначный ответ дают `uncertain`.
  `RandomIdDuplicate` также означает неопределённый результат, а не доказанный
  отказ. Такие сообщения нельзя автоматически отправлять с новым UUID.
- `FloodWait` возвращает структурированный `retry_after`. Необходимы
  планирование повторов и backoff на уровне воркера. Жёсткие ограничения или
  отзыв сессии требуют обработки оператором, а не циклического входа.
- `disconnect` вызывает Telegram `log_out`. При отказе отзыва credential
  сохраняется для повторной попытки. Обычный shutdown вызывает только `close`
  и не завершает авторизованную сессию на сервере Telegram.
- Подтверждённый отзыв ключа при подключении очищает только отозванную сессию
  и создаёт неавторизованное соединение для повторного входа кодом и 2FA.
  Курсор истории сохраняется. Временный `AuthKeyNotFound` не считается отзывом:
  ключ сохраняется, UI получает `telegram_auth_key_unavailable`.

## Границы текущей реализации

Текст до 4096 символов, облачные личные и групповые чаты, каналы, авторизация
кодом, QR и 2FA, постраничный импорт истории и получение новых сообщений реализованы.
Отправка в выбранный чат зависит от прав аккаунта в Telegram.
Вложения показываются понятной заглушкой и не скачиваются. Редактирования,
удаления, реакции, read receipts, звонки и секретные чаты в
этой версии не синхронизируются. Статус `sent` означает принятие Telegram,
а не прочтение клиентом. `connected` у sync означает поставленный импорт,
не завершение всех его страниц.

300 аккаунтов требуют отдельного соединения MTProto на аккаунт, распределения
владения аккаунтами между воркерами и отсутствия двух одновременных владельцев
одной сессии. Частоту polling и бюджет FloodWait нужно измерить на реальной
пилотной группе. В корпоративной сети нужны разрешённые подключения к
Telegram DC; обычный HTTP-only outbound proxy сам по себе MTProto не заменяет.

## Проверено

Модульные provider-contract тесты используют реальные TL-типы Telethon и
замоканные сетевые ответы: повторная доставка после потери commit, slice
cursor, native outbound, session replay, 2FA, стабильный nonce, FloodWait,
неопределённый timeout, отказ logout, ограниченный импорт, gap recovery,
первый контакт через resolvePhone, поиск при privacy denial, трёхсекундный
лимит lookup после перезапуска и защита при смене владельца номера. QR-тесты
покрывают ожидание, подтверждение, 2FA, переход между дата-центрами, возобновление
после перезапуска и ограничение времени ожидания. Проверяются административные
права, изоляция организаций, отсутствие секретов в ответах API, сохранение
личности после отключения и блокировка очереди при её несовпадении. Тесты миграции
проверяют сохранение шифротекста сессии и существующей очереди сообщений.

Это проверки кода и протокольных контрактов с подставленными ответами провайдера.
Реальный вход по номеру или QR и отправка сообщения в настоящий Telegram в этой
среде не выполнялись. После обновления стенда нужно проверить вход, 2FA,
входящие и исходящие сообщения на корпоративном тестовом аккаунте. Готовность
к 300 одновременно подключённым аккаунтам требует отдельного нагрузочного
прогона и проверки сетевого доступа к Telegram DC.

Источники протокола: [авторизация](https://core.telegram.org/api/auth),
[QR-вход](https://core.telegram.org/api/qr-login),
[получение обновлений](https://core.telegram.org/api/updates),
[getDifference](https://core.telegram.org/method/updates.getDifference),
[sendMessage](https://core.telegram.org/method/messages.sendMessage),
[Telethon](https://github.com/LonamiWebs/Telethon),
[условия Telegram API](https://core.telegram.org/api/terms).
